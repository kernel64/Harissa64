# Developing Harissa64 V2

How the emulator is built, tested and organised. Harissa64 V2 is a Nintendo 64 emulator for the Xbox 360
(Xenon PowerPC, Xbox 360 SDK, `.xex`), written from scratch.

Toolchains: Visual Studio 2010 with the Xbox 360 SDK (`%XEDK%`) for the console build; Visual Studio 2022+
(MSVC) with CMake and Ninja, or Linux gcc, for the host builds; `powerpc64-linux-gnu-g++` and `qemu-ppc64`
for the big-endian build that runs the recompiler under emulation. `<VS2010>` and `<VS2022+>` below stand for
the installation folders.

## Build and test

- **Everything**: `powershell -File tests\scripts\run_all.ps1` (add `-ExecMem` to also build the proof of concept; `-SkipWsl`, `-SkipXbox`). Prints `RESULT: ALL TARGETS OK` or the failing targets; exit code 1 on failure.
- **Windows host**: `cmd /c "<VS2022+>\VC\Auxiliary\Build\vcvars64.bat && cmake -S . -B build-msvc -G Ninja -DCMAKE_BUILD_TYPE=Release && cmake --build build-msvc && build-msvc\h64test.exe --unit"`.
- **WSL**: `wsl -d Ubuntu -- bash tests/scripts/run_wsl.sh` builds `build-gcc` (little-endian) and `build-ppc64` (big-endian, static, run with `qemu-ppc64`). Passing `$VAR`s through `wsl -- bash -c '...'` from PowerShell loses them: put commands in a script file.
- **Xbox 360**: from the PowerShell tool, `cmd /c '"<VS2010>\VC\vcvarsall.bat" x86 && C:\Windows\Microsoft.NET\Framework\v4.0.30319\MSBuild.exe platform\xbox360\harissa64v2.sln /p:Configuration=Release /p:Platform="Xbox 360" /m /v:minimal'`. Output: `platform\xbox360\Release\harissa64v2.xex` (the XDK platform imposes `$(Configuration)\` next to the project; `OutDir` overrides are ignored). Title ID `0x48413632` ("HA62"; V1 is `0x48413634`, the execmem tool `0x48413633`). `cmd //c` from the Bash tool silently does nothing: use PowerShell.
- **XDK command line without a project** (used by `tools\execmem\build.cmd`): `INCLUDE=%XEDK%\include\xbox;%XEDK%\include\xbox\sys`, `LIB=%XEDK%\lib\xbox`, `cl /c /TP /D_XBOX ...`, `link ... xapilib.lib d3d9.lib xboxkrnl.lib xgraphics.lib`, `imagexex /IN:x.exe /OUT:x.xex /CONFIG:xex.xml`. `dumpbin /disasm` (in `%XEDK%\bin\win32`) disassembles PowerPC objects.
- Build folders `build-msvc`, `build-gcc`, `build-ppc64`, `platform\xbox360\Release|Debug` are ignored.
- **Stale host objects**: cl prints "Remarque : inclusion du fichier :" with a non-breaking space in the console's OEM code page. A `build-msvc` configured from a console that recorded it otherwise (UTF-8) gets no header dependencies in Ninja: changing a struct rebuilds nothing that includes it, and runs crash or misbehave for no visible reason (twice on 2026-10-09). `ninja -t deps` shows `#deps 0`; `run_all.ps1` detects it and rebuilds the folder from scratch. After a reconfigure, also `cmake --build build-msvc --clean-first` (old objects stay "up to date").

## Test ROMs, games and the headless runner

- **Fetch** (never committed, `tests/roms/` is ignored): `python tests/scripts/fetch_test_roms.py`. n64-systemtest comes from a GitHub Actions artifact through `gh api` (artifacts expire: the current one on 2026-10-19; afterwards build it from source or take a newer run), Dillonb's tests from their release zip, PeterLemon/N64 at commit `7085543e` (CPUTest ROMs with their reference `.png` captures).
- **Score**: `python tests/scripts/run_suites.py [--runner "CMD"] [--suite dillonb|n64-systemtest|peterlemon] [--report FILE]`. Default runner `build-msvc/h64test.exe`; WSL: `--runner ./build-gcc/h64test` or `--runner "qemu-ppc64 ./build-ppc64/h64test"` (put the commands in a script file, see Build). PeterLemon ROMs are scored by comparing `--fb-png` with the hardware capture: channels on 5 bits, each reference line matched against our lines between the unscaled and the VI-stretched position (the captures are of the video output, sometimes 474 framebuffer lines shown as 480), pass at 99.9 %.
- **Commercial ROMs**: `tests/roms/commercial/*.z64` (local copies, ignored) for boot checks: `h64test --rom X --seconds 5` prints frames, instructions and RSP tasks.
- **h64test options** with `--rom` (a ROM, or a .zip holding one): `--frames N`, `--seconds S` (emulated), `--dillon` (pass/fail from r30), `--until TEXT` (stop on ISViewer text), `--info`, `--state` (registers, last jumps), `--trace-exc N`, `--watch-pc HEX`, `--jump-limit HEX`, `--stop-on-nops`, `--fb-png FILE` (VI output at the end), `--raw-png FILE` (the raw framebuffer the VI points at), `--shot FRAME:FILE` (VI output at a VI frame, repeatable), `--wav FILE` (every AI buffer as queued, 16-bit stereo), `--save-dir DIR` (game saves read from and written back to DIR; `--info` prints the console's save folder name), `--probe X,Y,FRAME` (every software-RDP write to pixel X,Y during VI frames FRAME and FRAME+1: combiner, blender, flags, colours, before/after), `--save-state FRAME:FILE` (state at the first quiet point from that VI frame), `--load-state FILE` (before the run; frames and input scripts go on from the state's frame), `[run] state hash` at the end, `--input SCRIPT` (controller 1: `BUTTON@first[-last]` in VI frames, comma-separated; buttons A B Z START L R DU DD DL DR CU CD CL CR, stick `X=n@..`/`Y=n@..`), `--verbose` (debug log, e.g. every PI DMA, RSP task starts, controller reads with a button held), `--cpu dynarec`, `--lockstep` (dynarec against the interpreter, first divergence), `--no-rdp` (RDP accepts commands but draws nothing: long CPU checks), `--hle-audio`, `--hle-gfx`, `--hle` (both), `--hle-audio-check` (HLE on an RDRAM copy per task, compared with LLE), `--null-renderer` (GPU-renderer configuration without a GPU: state-only RDP, triangles counted), `--trace-frames N [--trace-step C]` (state hashes every C cycles, same lines as the Xbox `trace=`; C = 1000000000 + START gives an instruction trace from cycle START), `--dump-ram FILE` (RDRAM then DMEM/IMEM at the end).
- **Game scenarios**: `python tests/scripts/run_games.py [--only NAME] [--update]` plays fixed scripts (title screens, SM64 up to Mario out of the pipe, MK64 up to a race) and compares SHA-1 hashes of the VI image and WAV with `tests/expected/games.txt`. Images and sounds stay in `build-suites/games/` (ignored): they are copyrighted, so only hashes are committed. To find a script, take `--shot` series and build a contact sheet (a scratch script tiles PNGs).
- **HLE boot** (`h64_hle_boot`, no PIF ROM or IPL3 run): copies 1 MB of ROM from 0x1000 to the entry point (6103: entry − 0x100000, 6106: − 0x200000), writes `osRomBase`/`osMemSize` and the boot registers (s3–s7, sp), DMEM = ROM[0..0x1000], PI timing from the header, RI values, and the state IPL3 leaves behind that test ROMs read: Cause `0xB000007C`, LLAddr `0xFFFFFFFF`, PI DRAM/CART `0x00101000`/`0x1000000C`, both PI lengths `0x7F`.
- **IPL3 boot for 6105 cartridges** (`ipl3_boot`: OoT, Banjo-Tooie, Conker, Perfect Dark, DK64, JFG, Mickey...): the real IPL3 runs from DMEM after what the PIF ROM leaves (mupen64plus `pif_bootrom_hle_execute`: IPL3 in DMEM, 8 words of IPL2 in IMEM, s3–s7, t3, sp, ra). The 6105 IPL3 decrypts itself and starts an RSP program that waits on SP_SEMAPHORE for the 1 MB PI DMA, then writes 24 words into RDRAM which these games check (DK64: 0x2FE1C0 == 0xAD170014; they loop forever without). That only works with the RSP pipeline timing (below): one instruction per cycle made the RSP give up before the DMA ended. The IPL3 sizes memory itself: `H64Ri.rdram` emulates the four 2 MB RDRAM modules' registers (device ID / address-select matching, broadcast, power-on values) and, while a module calibrates its current (CE set, CC = 0), RDRAM reads return 0 (`ri.corrupt`, bus reads only; the IPL3 runs from DMEM, so through the interpreter even with the dynarec). Without that, osMemSize stayed 0 and DK64 showed "Expansion Pak not installed". ~7 M RSP instructions at boot: about 4 s on the console (LLE RSP).
- **Timing model**: one CPU instruction per CPU cycle, Count = cycles / 2; PI DMA blocks and duration from ares (RCP cycles × 1.5); the RSP runs in lockstep with the CPU (2 RCP cycles per 3 CPU cycles) with ares's pipeline model: one issue group per RCP cycle, a vector and a scalar instruction may dual-issue, stalls when a register written by a load/MFC0/MFC2/CFC2 is read in the next groups (2, then 1 cycles; vector registers 3/2/1), a store right after a load, and a taken branch's delay slot (`h64_rsp_issue`, decode cache `sys->rspDecode` at the end of H64System); SP DMA one RCP cycle per 8 bytes; the RDP runs each command at once when DPC_END is written (no time passes), shows PIPE_BUSY|START_GCLK from the first command until SYNC_FULL, and raises the DP interrupt at SYNC_FULL.
- **Controllers**: ports 1-4 (`sys->pad[4]`, `sys->padMask`: bit n = a controller on port n + 1; 0 counts as port 1 only); an empty port answers "no response" to info/read, as on the console (games count their players from it); the Controller Pak is on port 1. Xbox: XInput controller n is N64 port n + 1, port 1 always plugged in, ports 2-4 while connected (`padMask` refreshed at every poll, before the games' probes); the BACK shortcuts stay on controller 1. h64test `--pads N` plugs ports 1..N (scripts drive port 1). The JoyBus block runs on an SI write when the control byte asks for it, and the controller commands run again on every SI read, because libultra writes the block once and then only reads (mupen64plus `update_pif_read`). 
- **Save states** (`core/savestate/h64_state.cpp`): one visitor lists every field for the save, verify and load passes; each field is written big-endian, so states are portable between the console, Xenia and the hosts (checked: a host state loads on the console; a ppc64 state continues on the hosts with the same CPU hash). Taken only at a quiet point (`h64_state_quiet`: no HLE task in progress), so the RSP HLE keeps nothing a state needs, as in mupen64plus. Loading first verifies the whole state (bad data leaves the machine alone), waits for the workers, then resets the recompiler, the RSP HLE and the renderer (`H64Renderer::reset`: frame slots dropped, textures kept). Includes the save media. Bump `H64_STATE_VERSION` whenever a field is added. Check: `python tests/scripts/state_check.py RUNNER ROM FRAMES SAVEFRAME OUTDIR [h64test args]` (straight run vs save + load in a new process: same CPU/RAM hash and image; SM64 HLE and LLE, MK64, OoT). Known: ppc64 and x86 builds differ in RDRAM after the same run (floating-point rendering), states or not.
- **Game saves** (`core/cart/h64_save.cpp`, `sys->save`, kept across resets): EEPROM on JoyBus channel 4, Controller Pak commands on port 1 (plugged in when the catalogue says the game uses one, or the game is unknown), SRAM/FlashRAM on domain 2 (CPU accesses and PI DMAs, plain copies). Save type from `h64_savedb.inc` (regenerate with `python tests/scripts/gen_savedb.py`); unknown cartridges: EEPROM 4K, and domain 2 becomes FlashRAM if the first access is a command write to 0x08010000, SRAM otherwise. The core marks `dirty`/`used`; the platform stores the files. The Xbox uses `<drive>:\saves\<name> <game code>\{eeprom,sram,flash,pak1}.bin` (`h64_save_folder_name`), written 2 s after a change and when leaving.

## RSP, RDP and VI (M2)

- **RSP** (`core/rsp`): LLE interpreter ported from ares (ISC), scalar paths only. Vector registers are 8 × u16 with element 0 first in memory order; flags are 0/0xFFFF per element; `vbyte()`/`vset_byte()` give the byte view. MFC0/MTC0 reach the SP registers (0–7) and the DPC registers (8–15) through the normal register handlers. Reserved vector opcodes behave as ares's VZERO (PeterLemon's 6 RESERVED tests fail on the accumulator value, games never use them).
- **RDP** (`core/rdp`): `h64_rdp.cpp` is the command interface (DPC registers, fetch from RDRAM or DMEM with XBUS, multi-word assembly); `h64_rdp_render.cpp` and `h64_rdp_tex.cpp` are a serial port of ParaLLEl-RDP's compute shaders (MIT), which are bit-exact with the hardware: per primitive, every line of `[max(yh, scissor.ylo) >> 2, min(yl - 1, scissor.yhi - 1) >> 2]` gets a span (span_setup.comp), every pixel of the span is shaded (shading.h) and immediately depth-tested, blended and written to RDRAM (depth_blend.comp), which gives the in-order result. The shaders address TMEM "physically" (32-bit little-endian words: bytes XOR 3, halfwords XOR 1); our TMEM is in N64 order and `tm8()`/`tm16()` translate, so the ported expressions stay as written. TMEM loads are not ported (ParaLLEl does them as a GPU gather): they walk the load in 64-bit words as the hardware does (odd lines swap 32-bit halves; 32-bit and YUV textures split RG/BA or UV/YY between the TMEM halves; TLUT entries written 4 times). RDRAM's 9th bits live in `sys->rdramHidden` (one byte per halfword, initialised to 3): coverage for 16-bit framebuffers and the low dz bits of the Z buffer. Signed arithmetic must wrap (GLSL semantics): gcc builds use `-fwrapv`. angrylion-rdp-plus is under the MAME licence (not GPL-compatible): don't use it.
- **VI** (`core/vi`): `h64_vi_render()` ports ParaLLEl-RDP's VI (fetch with coverage, AA filter, dither filter, divot, bilinear scaler, gamma and gamma dither) and produces what the console sends to the TV: 640 × 240 per progressive frame (288 PAL), 640 × 480 interlaced. Simplifications: registers constant for the frame; an interlaced frame uses the current registers for both fields; the "fetch bug" (YAdd < 1.0) is not emulated. PeterLemon's reference PNGs are raw framebuffer dumps, not VI output: the suites score `--raw-png`.
- **Audio**: `sys->aiSink` receives each AI buffer when the game queues it (with AI DMA enabled); M2 only dumps it to WAV.
- **Speed** (host, reference path, i7-11800H, MSVC Release): about 0.4× real time on SM64's title (6 s emulated in 16 s). The console path (M3/M4) uses the dynarec and HLE instead.

## Dynarec, HLE and the Xbox front end (M3, M4)

- **Dynarec** (`core/dynarec`): blocks of up to 64 instructions inside one 4 KB page, keyed by virtual PC plus a physical-address and kernel-mode check. Every RDRAM writer invalidates only the blocks it overlaps (`h64_jit_invalidate`); native stores take the slow path only on 64-byte chunks that hold code (`codeMap`, a count per chunk). Native code: ALU, shifts, HI/LO, multiplies, DIV/DIVU, branches and jumps (BC1 included), loads/stores with an RDRAM fast path (LWC1/LDC1/SWC1/SDC1 too), MFC0/DMFC0 (not Random), COP1 moves, and COP1 arithmetic, compares, conversions, ABS/NEG on the host FPU when the result is certain to be the interpreter's (operands normal or zero, guest rounding mode nearest, FPSCR shows no flag but inexact, normal result; FI gives Inexact), else the interpreter. **FPR cache**: once a block knows Status.CU1/FR (`fpu_guard`), COP1 registers (by `fgr[]` index) stay in host FPRs like the GPRs (`RegCache.fhost`...): f14-f31 (saved by the shared prologue, frame 448 bytes) then f6-f13 (volatile: reloaded after slow-path calls); an entry is the whole register as a double or the low word as a single (lfs/stfs and lfd/stfd are bit-exact), a single result also zeroes the high word when written back (`fhiz`), LWC1 keeps it; LWC1/LDC1/SWC1/SDC1 use lfsx/lfdx/stfsx/stfdx on RDRAM; MFC1/MTC1/DMFC1/DMTC1, CVT from W, odd registers with FR = 0 and a read in the other format go through H64Cpu (entry written back first). Every exit and interpreter call writes back the dirty entries; slow paths store/reload them through `rtFcStore`/`rtFcLoad` with a slot table after the call (cold code filled its region on DK64). DK64's matrix block 0x8061A938: 90 lfs + 45 stfs + 55 stw -> 10 + 18 + 13 (fast FPU: 439 -> 242 PPC words). h64test `--no-fp-cache`, ini `fpcache=0`. Everything else calls the interpreter for one instruction (`--jit-ops` lists them). A block runs only if no event falls inside it; exact idle-loop skipping. **Block linking**: an exit with a fixed next pc checks that no event and not `runEnd` fall within the next 64 instructions, then goes on: the first time through the dispatcher, which patches the exit into a direct branch to the next block's body (links undone when the target is invalidated; any invalidation stops the running block; idle-loop blocks are never linked). A linked exit whose instructions are all done is compact: `li r3,cycles; li r4,insns; bl rtLink; beq +8; b <event tail>; b <next>`; `rtLink` adds the counters and checks events/runEnd; pc/nextPc are written only by the cold tails. The event tail must not offer the exit for linking (it may be linked already): offering it added a link record per event until the table was full (DK64 with the graphics worker: 147000 dispatcher trips a frame instead of 2000, 11 FPS instead of 25). Exits after a load/store, FPU or overflow-checked delay slot keep the full inline form (the compact one diverged on Conker; `fullExits` / h64test `--full-exits` / ini `fullexits=1` use the full form everywhere, for A/B checks). Link records are reused (free list; `link_exit` never records an exit twice): Conker relinks tens of thousands of exits a frame and the 65536 records were gone within seconds, after which nothing linked. The dispatcher translates KSEG0/1 pcs directly, and TLB-mapped pcs through a 256-page cache (`H64Jit.fetch`: each entry remembers the TLB entry it came from and stays valid while that entry (`cpu.tlbEntryGen[i]`) and the ASID (`cpu.asidGen`) are unchanged; misses use `h64_cpu_probe_fetch`, no side effects). Links into TLB-mapped code are allowed and recorded per TLB entry (`H64Jit.tlbLinks`): when an entry (or the ASID) changes, the dispatcher re-probes each link through it and keeps it if the target's virtual pc still maps to the block's physical address (an entry maps two pages; Conker refills its TLB constantly: undoing every link ran it at 1 FPS); TLB writes that leave an entry unchanged do not bump its generation; a block stops after any TLB write (`cpu.tlbGen` in `h64_jit_should_exit`). **Indirect jumps**: a native `jr`/`jalr` exit goes to `rtIndirect`, which checks events/runEnd like a linked exit and jumps into the target block found in `indPc`/`indBody` (1024 entries by pc bits 2..11, filled by the dispatcher for native KSEG0/1 blocks, dropped with their block); Dr. Mario 22 -> 32 FPS. Fields read by generated code must stay below 32 KB in H64Jit (static_asserts). `h64_cpu_translate_debug` copies the whole H64Cpu: never on hot paths (it made Perfect Dark run at 8 MIPS). `--lockstep` with `--load-state` loads the state into both systems; `--async CYCLES` takes the Xbox's worker path for HLE tasks (jobs run at once). `cpu.cpi` (h64test `--cpi`, ini `cpi=`) sets CPU cycles per instruction (h64test default 1; the Xbox front end defaults to 2 = mupen64plus's CountPerOp 1, and to `fastfpu=1` since 2026-10-09: DK64 25 -> 60 FPS, Dr. Mario 32 -> 60); the shared routines and the blocks are regenerated when it differs from what they were made for (`rtCpi`: the front end sets cpi after `h64_jit_init`). ABIs: ELFv1 (ppc64 Linux, QEMU) and Xbox. Xbox code cache: 32 MB static array in the `.jitc` ERW section (the xex grows by as much; hot code in the first 5/12, slow paths in the rest (they take ~1.4 times the hot code), all within a relative branch; 16 MB filled every ~40 s on DK64/Conker, `[jit] code cache full` logs a flush) (code there runs as fast as `.text`, measured at start-up: `[jit] code memory`). Lockstep (`--lockstep`) is the reference check: clean on Dillonb, n64-systemtest, SM64, MK64 race 43 s, OoT 3000 frames under QEMU. h64test `--no-link`, `--no-jit-fpu`, ini `jitfpu=0`.
- **RSP task HLE** (`core/hle`): `h64_hle_try_task` runs when the RSP leaves halt at PC 0; audio (`options.hleAudio`) and graphics (`options.hleGfx`) tasks run at once in C++, the RSP stays "busy" `H64_HLE_*_CYCLES` CPU cycles, then halts with break/task-done and its interrupt (and the DP interrupt after an RDP full sync). Unknown tasks and microcodes go to the LLE RSP. The graphics HLE buffers its RDP output and sends it only when the whole display list ran (a G_LOAD_UCODE to an unknown microcode falls back to LLE for the task). Rare's F3D variants are recognised by the CRC-32 of the first 4 KB of microcode code, computed on byte-reversed words as GLideN64 does (`detect_ucode`): GoldenEye (G_TRIX 0xB1: four triangles; G_MOVEWORD also at 0xBD), Perfect Dark (12-byte vertices with a colour/normal index into G_VTXCOLORBASE's table, G_TRIX), Diddy Kong Racing / Jet Force Gemini / Mickey's Speedway (DMA matrices in 4 model-view slots with identity projection, 10-byte DMA vertices, 16-byte DMA triangles with their own s/t and cull flag, billboards relative to vertex 0, G_DMA_DL counted display lists, texture-offset tables), Conker's Bad Fur Day (F3DEX2 with 4-triangle commands 0x10-0x1F, normals from a G_MV_NORMALES table plus the vertex flag, 48-byte lights with positions: ambient + point lights + in the advanced mode (its G_LOAD_UCODE) a directional one, coordinate modifiers). Texture generation (G_TEXTURE_GEN) produces s/t in texels: ×32 into the vertex's s10.5 units (MK64's and GoldenEye's shiny logos were dark). S2DEX2 is handled for what OoT's prerendered rooms use (G_BG_COPY in copy mode, emitted as the microcode's LoadTile/TEXRECT strips; same image as LLE on Link's house); any other S2DEX command leaves the task to LLE. Audio HLE is upstream's, not bit-exact with LLE (see PROGRESS.md).
- **Xenos shading as the RDP does it**: shade (colour and the fog factor in its alpha) is interpolated linearly in screen space, not perspective-correctly (the VS sends shade*w and w, the combiner divides); in the second combiner cycle TEXEL0 is texel 1 and TEXEL1 texel 0 (the combiner text swaps `t0`/`t1`). Both were needed for OoT's Kokiri paths (pale fogged ground that changed with the camera angle).
- **Finding a rendering bug**: take a save state at the spot, replay it on the console (`loadstate=1`, `input=`, `shots=`) and on the host (`--load-state`, `--shot`), compare pixels, then `h64test --probe X,Y,FRAME` logs every software-RDP write to that pixel with the full mode.
- **Copy-backs** (a frame the GPU drew read back into RDRAM, when the game uses it as a texture): the frame is drawn at the N64 size into a small EDRAM target (`EDRAM_READBACK`, 640x480 max), resolved into a `D3DUSAGE_CPU_CACHED_MEMORY` texture, its cache lines dropped with `__dcbf`, then untiled; reading the full 960x720 frame from write-combined memory cost ~18 ms each (Paper Mario: 6 FPS in transitions). Pixels are written in the colour image's own format (`store_pixel`: RGBA5551, RGBA8888, IA88, I8; I4 images are not copied back) and only over the lines drawn (`FbSlot.drawnH`, from the scissor and fills; the height guessed from the width only sets the scale): 8-bit images copied as 16-bit wrote past themselves and froze Conker on its copyright screen. `xenosdebug=5` disables copy backs (diagnosis). An address can lie in several frame slots (an older, bigger image covering a newer one: DK64's 640x480 intro buffers span its 320x240 ones): the VI and copy-backs take the most recently drawn slot (the first match showed a black frame every other game frame). `xenosdebug=6` logs the VI origin and the slots once a second.
- **Renderer teardown**: `h64_xenos_free` unbinds textures, shaders and the vertex declaration and waits for the GPU before releasing them (the device keeps no reference: the next game's renderer crashed otherwise).
- **Texture arena** (`arena_alloc`): textures up to 1 MB get a D3D header (`XGSetTextureHeader` + `XGOffsetResourceAddress`) over 24 MB of `XPhysicalAlloc` write-combined memory, used in 1 MB chunks in a ring; re-entering a chunk that holds textures of an earlier lap unbinds both units, waits on a fresh fence (`BlockOnFence(InsertFence())`), drops its textures from the cache (headers deleted), `InvalidateGpuCache` on the chunk, and counts as a retire (unit 0 rebound). Rows 256-byte aligned, data 4 KB aligned, `__sync()` after the copy. CreateTexture cost ~400 us each on the console (GoldenEye's gun-barrel intro: ~300 new small textures a frame, 110 ms; now ~2 ms). Bigger textures keep CreateTexture and the size pool. Texture keys hash only what the decode reads (not the tile position).
- **Xenos texture cache**: `retire_all_textures` (cache full) waits for the GPU, moves every texture to the pool and binds the dummy (white) texture on both units; `setup_combined` rebinds unit 0 when that happened while binding unit 1.
- **Renderer** (`render/api.h`): `sys->renderer` NULL means the software RDP (HLE triangles become RDP triangle commands, `h64_rdp_build_triangle`). The Xenos renderer sets `options.rdpStateOnly`: the software RDP keeps state and TMEM but draws nothing; Xenos draws from that state (textures decoded with `h64_rdp_fetch_texel`).
- **Xbox front end** (`platform/xbox360/main.cpp`; `xb_config.*` the settings, `xb_ui.*` text/panels/button prompts and the pepper logo (`UiLogo`, pixel art) drawn with Clear rectangles, `xb_menu.*` the ROM browser, menu panels and settings screen), configured by `game:\harissa64v2.ini` (`key=value`): `mode=play|jittest`, `cpu=dynarec|interp`, `hle=1|0`, `rom=PATH` (else `game:\test.z64`, else the first ROM in `game:\roms\`), `renderer=soft` (diagnosis), `shots=f1,f2` (BMP of the shown frame at those VIs, next to the log), `exitafter=N`, `pauseat=N` (hold frame N for 20 s), `trace=N`/`tracestep=C`, `xenosdebug=1..4` (4: log each drawing mode once), `jitfpu=0`, `regcache=0`, `fpcache=0`, `cpi=N`, `smooth=0`, `fpuflags=0`, `xenia=1` (no FPSCR access, no dashboard return), `stateslot=N`, `loadstate=1` (load that slot at start), `savestateat=N` (save at VI N), `menuat=N` (open the in-game menu at VI N), `aboutat=N` (the same on the About panel: credits, version, licence; also X in the ROM browser), `autostart=N` (the browser starts N games itself: the last selection, then the next ones), `browserat=N` (back to the ROM list at VI N), `showfps=1`, `audioms=N`, and the Graphics page's keys: `resolution=1|2|3` (internal resolution: the N64 target's top-left 320x240 / 640x480 / 960x720 through the viewport; scissors, fills, copy-backs and the display use `rtW`/`rtH`/`uMax`/`vMax`), `aspect=0|1|2` (4:3; 16:9 widescreen: the x of 3D and of small 2D elements moved 3/4 towards the centre (`ws_x`), full-width fills, rectangles, scissors and edge-to-edge 2D triangles (MK64's sky) kept, the picture shown across 16:9: wider scene, no distortion, objects the game culls stay missing; no phosphor mask: the console scales the 1280x720 picture to 1080p by 1.5 and any mask beat into coloured vertical bands, measured on front-buffer captures), LCD grid, light scanlines; the CRTs sample the picture without FXAA/blur/sharpen: with them the Xenos microcode compiler ran out of registers after 20-40 s and the console looked frozen; check display shaders offline with the XDK's `fxc /T ps_3_0`), and four presets in the menu (Original, N64 Enhanced, N64 Smooth, N64 CRT). The display shader is generated per combination and cached (`display_shader`); sampling is clamped to the drawn part (a column of garbage at the right edge). Front-buffer captures for checks: `xbcapture /x <console> file.bmp` (the console outputs 1080p). **Start-up**: with `rom=`, `game:\test.z64` or any scripted key (`input`, `shots`, `exitafter`, `trace`, `loadstate`, `savestateat`, `menuat`) one game runs with harissa64v2.ini alone; otherwise the **ROM browser** lists `game:\roms\` (.z64 .n64 .v64 .zip: the first N64 ROM inside a zip, inflated straight from the file) and the menu's files apply over harissa64v2.ini: `<drive>:\config\settings.ini` (all games, also `lastrom=`) then `<drive>:\config\<game folder>.ini` (profile; same name as the save folder). **In-game menu**: a short BACK press (released within 600 ms, no RB/LB/D-pad) pauses and shows it over the frozen frame (`GameMenu`: waits for the graphics worker, then presents on the CPU thread with the overlay); settings apply at once (audio margin, smoothing, FPS) or at the next start (CPU, RSP). **Pacing**: each frame waits on the clock (QPC) for one VI period, nudged by up to 1 % by the audio queue's fill (XAudio2's rate control keeps the queue near its target); far over the target it drains. Pacing on the audio queue alone ran frames in bursts (Paper Mario's name screen: intervals 2-130 ms). `[pace]` lines: present intervals (mean, sd, min, max) and the longest time of each loop section. **Logging on the console**: the sink only appends to memory; a thread on hardware thread 5 writes the file every 500 ms (warnings/errors at once); never `OutputDebugString` (with XBDM loaded each line goes to the debug monitor, ~9 ms: 100+ ms stalls every 2 s). **Measuring time on the console**: use QPC; GetTickCount and the system clock fall behind while the emulator runs, and a log flushed per line costs ~120 ms per period on a USB stick (the sink flushes warnings/errors only, `LogFlush` once per period). `[perf]`, `[prof]`, `[cprof]`, `[xprof]`, `[jit]`, `[xtex]`, `[pc]` (N64 PC sampler) and `[state]` lines every 2 s; at start-up `[jit] code memory` and `[jit] code locality` (cost of far jumps). Audio paces the emulation (XAudio2 queue target `audioms=`, default 500 ms since 2026-10-09 (sound cuts at 250 in the Rare games; 64 queue slots of one game buffer each), 250 before: on OoT, 100 ms as in V1 gave about one underrun per 2 s, 150 ms 3 in 76 s, 200 ms 2; playback rate steered 0.90–1.02 toward it, re-buffering at 60 % of the target after an underrun), the clock does when no sound plays. The shown frame goes through FXAA (`smooth`). **Graphics worker** (`asyncgfx=1`, default): graphics HLE tasks and the presents run in order on hardware thread 2 beside the CPU thread; a task's end stays at a fixed emulated time (`gfxcycles`, 400000) where the CPU thread waits for it (deterministic); the D3D device changes thread with `AcquireThreadOwnership`; anything else using the renderer waits for the worker first (`h64_hle_async_wait`).
- **EDRAM layout**: 1280x720 back buffer (tiles 0..719), N64 colour target 960x720 (from tile 720), its depth (from tile 1260). N64 frames are resolved into tiled textures (one per colour image) and the one the VI shows is drawn 4:3 on the back buffer at each VI.

### Xenia findings (M4)

- Xenia does not emulate the PowerPC FPSCR exception flags (they read back all set): every guest FPU operation raised an exception and SM64 stalled at boot. `h64_fenv_init` self-tests the host flags and reports none when they fail (`[fpu] host exception flags are not reliable`).
- A Resolve into a `LIN` texture comes out scrambled: frame textures are tiled; screenshots untile with `XGUntileSurface`.
- Resolves reach guest memory only with `--readback_resolve=true` (needed for the xex's own screenshots in Xenia).
- "Title Launch Failed: path is invalid ... default.xex" in Xenia comes from `XLaunchNewImage(XLAUNCH_KEYWORD_DEFAULT_APP)` when the title ends (Xenia has no dashboard): the front end skips it when the FPU self-test says Xenia.
- Window captures of Xenia: `PrintWindow(hwnd, hdc, PW_CLIENTONLY | PW_RENDERFULLCONTENT)`; `CopyFromScreen` grabs whatever window is on top.
- Speed with the interpreter (Xenia cannot run generated code): about 5–6 VI/s.

## Core language subset (XDK compiler probe, M0.2)

The core and everything shared with the Xbox build must compile with the XDK's cl 16.00 (VS2010). Probe: one file per feature compiled with `/c /TP /EHsc /GR /O2 /D_XBOX` and the XDK headers (October 2026).

**Allowed**: `auto`, `nullptr`, `static_assert`, lambdas (value and reference capture), `decltype`, rvalue references and `std::move`, `enum E : u8` (typed unscoped enums), `override` (MSVC extension), `long long` (also in `switch`), `<stdint.h>` and `<cstdint>`, anonymous unions, local structs as template arguments, `__declspec(align(n))`, `__alignof`, `__restrict`, `__forceinline`, `_byteswap_ulong`, `std::unique_ptr`, `std::shared_ptr`/`make_shared`, `std::function`, `std::unordered_map`, `std::vector`/`std::string`, `<algorithm>`, `std::array`, `<type_traits>`, C++ exceptions, RTTI/`dynamic_cast`, `__try/__except` (with `<xtl.h>`), `<ppcintrinsics.h>` (`__loadwordbytereverse`, `__dcbst`, `__dcbf`, `__sync()`, `__lwsync()`, `__emit()`, `_CountLeadingZeros`, `__mulh`), `<vectorintrinsics.h>` (VMX-128 `__vector4`, `__vaddfp`), Win32-style threads (`CreateThread`, `XSetThreadProcessor`, `Interlocked*`).

**Not allowed**: `enum class`, range-based `for`, `constexpr`, variadic templates, `final`, `alignas`, `= default`/`= delete`, non-static data member initialisers, brace/uniform initialisation of objects, `std::initializer_list` construction (`std::vector<int> v = {1,2}`), template aliases (`using X = ...`), explicit conversion operators, `char16_t`/`u''`, `<thread>`, `<atomic>`, `<mutex>`, `<chrono>`, `<inttypes.h>`.

**C files** (`.c`) are C89: no declarations after statements, no `for (int i...)`, no `inline` (use `__inline`), no `<stdbool.h>`, no designated initialisers, no VLAs (`//` comments are fine). V2 writes the core in `.cpp` only.

There is **no `icbi` intrinsic** and no inline assembly: emit raw words with `__emit()` in a `__declspec(noinline)` function whose argument arrives in `r3` (see `FlushLine` in `tools/execmem/execmem.cpp`, checked with `dumpbin /disasm`), or call the kernel's `KeSweepIcacheRange`.

The host builds use C++11 (`CMAKE_CXX_STANDARD 11`) and cannot enforce this subset: the Xbox build in `run_all.ps1` is the check.

## Conventions

- **Endianness**: guest memory (RDRAM, ROM, RSP DMEM/IMEM, PIF RAM...) is a byte array in N64 order; a guest byte address is a host byte offset on every target. Multi-byte guest accesses go only through `core/common/h64_endian.h` (`h64_load_be16/32/64`, `h64_store_be*`; `h64_ref_*` are the byte-by-byte reference versions, tested against the fast ones). No raw casts of guest memory pointers elsewhere. `H64_HOST_BIG_ENDIAN` is 1 on the Xbox and the ppc64 build.
- **Pointer size**: 32 bits on the Xbox, 64 on the hosts. Never store pointers in `u32`.
- **Unique source file names** across `core/` and `tests/unit/`: the Xbox project compiles them by wildcard into one object folder.
- **Logging**: the core calls `H64_INFO/WARN/ERROR/DEBUG`; the platform installs a sink (`h64_log_set_sink`).
- **Unit tests**: a `void test_x(H64TestContext *ctx)` function using `H64_CHECK`/`H64_CHECK_EQ`, declared and listed in `tests/unit/unit_tests.cpp` (no static registration: the XDK linker drops unreferenced objects). Every target runs the same list: `h64test --unit` on the hosts and under QEMU, and the Xbox build at start-up.
- **Version**: `VERSION` at the root (`2.0.0-dev`), passed as `H64_VERSION` by CMake and by the vcxproj; `H64_VERSION_STRING` in `h64_version.h`.
- Never commit ROMs, saves or downloaded test ROMs.
- Licence GPL v2. Anything ported or closely followed gets a provenance comment and an entry in `THIRD_PARTY.md`; GPL v3-only code (gopher64) may be studied, never copied.
